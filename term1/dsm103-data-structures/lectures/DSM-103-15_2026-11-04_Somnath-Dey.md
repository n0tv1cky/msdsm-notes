# DSM-103 Lecture 15: Heap Trees, Heap Sort, and Threaded Binary Trees

**Session:** DSM-103-15 · 2026-11-04 · Instructor: Somnath Dey

---

## 1. Overview

This session introduces the **heap tree** (binary heap). The motivation is that a binary search tree suits searching, but it degrades to $`O(n)`$ on skewed (sorted) input. A BST also cannot naturally model *priority*, as in a priority queue for printer jobs or memory allocation.

The lecture covers:

- The two defining heap properties: the ordering property (max-heap or min-heap) and the shape property (complete or almost complete).
- Array representation with exact index formulas for 1-based and 0-based arrays.
- **Insertion**, which sifts the new node up.
- **Deletion**, which always removes the root and then sifts down.
- **Heap sort**, built from repeated deletions, with a full worked trace.

The final part of the session introduces **threaded binary trees**. These reuse the $`n+1`$ null links of a linked binary tree to store in-order predecessor and successor pointers, with one tag bit per link.

---

## 2. Topics and Concepts (in order taught)

### 2.1 Motivation: Why a Heap?

**Limitations of the BST:**
- A BST gives efficient search in $`O(h)`$, which is $`O(\log n)`$ when the tree is balanced.
- If the data is sorted, the tree becomes left- or right-skewed, and search degrades to $`O(n)`$.

**Priority queue example (office printer):**
- Many employees submit jobs to one printer.
- Jobs from top management should print first, according to the hierarchy.
- A BST does not maintain this kind of priority ordering. A heap does.

**Memory management example:**
- Pointers to free memory blocks are kept in a heap.
- When memory is requested, it is allocated from the heap. For example, the largest free block is handed out first, which is a max-heap use case.

### 2.2 Definition of a Heap Tree

A heap must satisfy **two properties**.

**Property 1: Heap-order property (recursive definition).**
Every node's value is greater than or equal to (max-heap), or less than or equal to (min-heap), the values of its children.

- **Max-heap:** $`\text{key}(\text{parent}) \ge \text{key}(\text{child})`$ for every node. The root holds the maximum.
- **Min-heap:** $`\text{key}(\text{parent}) \le \text{key}(\text{child})`$ for every node. The root holds the minimum.
- Left versus right placement does **not** matter. There is no ordering between siblings, unlike a BST.
- **When to use a min-heap:** when a lower value means higher priority. For example, rank 1 is first priority.
- **When to use a max-heap:** when the largest value should be served first. For example, the largest memory block is allocated first.

**Property 2: Shape property.**
The tree must be **complete** or **almost complete**.

- *Complete:* every level, except possibly the last, is completely filled.
- *Almost complete:* the last level is filled **from the left**, with no gaps.
- **Example from class:** adding 15 as a child at a position whose left sibling is missing violates the shape property. Such a tree is **not** a heap, even if the order property holds.

**Example max-heap used throughout the lecture** (described in words):
- The root is 95.
- 95 has left child 85 and right child 45.
- 85 has children 75 (left) and 25 (right).
- 45 has children 35 (left) and 15 (right).
- 75 has children 55 (left) and 65 (right).
- Every parent is greater than its children, and the last level is filled from the left.

**Min-heap example:**
- The root is 15, with children 45 and 25.
- Swapping 45 and 25 would still be fine, because sibling order does not matter.
- The instructor also showed a non-example: a node deeper in the tree had a value greater than its child 35. That breaks the min-heap property, so that tree is **not** a heap.

**Purpose of a heap:** fast access to the maximum element (max-heap) or the minimum element (min-heap). That element is always at the root.

### 2.3 Operations Allowed on a Heap

- **Deletion always removes the root.** You do not delete an arbitrary node, because a heap cannot be searched efficiently. For example, if you look for 35, you cannot tell whether it is in the left or the right subtree.
- **Removing the root** costs $`O(1)`$. **Restoring the heap** afterwards costs $`O(\log n)`$, so a complete delete operation is $`O(\log n)`$.
- **Insertion** places the new node at the next position that keeps the tree complete or almost complete. Nodes are then rearranged to restore the heap order.

### 2.4 Array Representation of a Heap

**Why use an array:**
- Because a heap is always complete or almost complete, an array represents it with **no gaps**. This makes the array the efficient representation.
- Trees that are not complete are better stored with a linked representation.

**Index formulas, 1-based array (the convention used in class; the root is at index 1):**

```math
\text{left}(i) = 2i, \qquad \text{right}(i) = 2i+1, \qquad \text{parent}(i) = \left\lfloor \frac{i}{2} \right\rfloor
```

- With 1-based indexing, **left children are always at even indices** and **right children at odd indices**.
- The parent formula uses **integer (floor) division**. For example, $`\text{parent}(5) = \lfloor 5/2 \rfloor = \lfloor 2.5 \rfloor = 2`$.

**Index formulas, 0-based array:**

```math
\text{left}(i) = 2i+1, \qquad \text{right}(i) = 2i+2, \qquad \text{parent}(i) = \left\lfloor \frac{i-1}{2} \right\rfloor
```

> **Caution from class:** a student proposed $`\lfloor (i-1)/2 \rfloor`$ for the parent. The instructor clarified that this formula is valid **only for 0-based indexing**. With the 1-based convention, use $`\lfloor i/2 \rfloor`$.

**Worked layout of the example max-heap (1-based):**

| Index | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 |
|---|---|---|---|---|---|---|---|---|---|
| Value | 95 | 85 | 45 | 75 | 25 | 35 | 15 | 55 | 65 |

- Check the formulas: index 2 (85) has children at $`2\cdot2=4`$ (75) and $`2\cdot2+1=5`$ (25).
- All elements occupy contiguous positions, which confirms the tree is almost complete.
- If a middle node were missing (for example, 85 absent), there would be a blank slot in the array. That tree would **not** be complete or almost complete.

**Scope note:** row-major and column-major 2D-array addressing was **not** covered in this session. The only addressing formulas taught are the heap index formulas above.

### 2.5 Insertion (Sift-Up / Bottom-Up Heapify)

**Algorithm (max-heap, 1-based array `A`, current size `n`):**

```
INSERT(A, n, key):
    n ← n + 1
    A[n] ← key                      // next free slot keeps the tree almost complete
    i ← n
    while i > 1 and A[⌊i/2⌋] < A[i]:   // compare with parent, bottom-up
        swap A[i], A[⌊i/2⌋]
        i ← ⌊i/2⌋
    return n
```

**Worked example (starting from the 9-node heap above):**

1. **Insert 19.**
   - The next free slot is index 10, which is the left child of 25 (index 5).
   - Compare with the parent: $`19 < 25`$, so the heap property holds and nothing more is needed.
2. **Insert 111.** (The transcript says "100 11"; the value is 111.)
   - The next free slot is index 11, the right child of 25. The shape property holds.
   - $`111 > 25`$, so swap. 111 is now a child of 85.
   - $`111 > 85`$, so swap. Its sibling 75 does not need checking, because 75 was already less than 85.
   - $`111 > 95`$, so swap. **111 becomes the root.**
3. **Insert 120.**
   - Students first guessed "left of 55", but that is wrong. The level must be filled left to right, so the next free slot is index 12, the **left child of 35**.
   - $`120 > 35`$, so swap.
   - $`120 > 45`$, so swap.
   - $`120 > 111`$, so swap. **120 becomes the root.**

**Complexity:**
- The maximum number of comparisons equals the height $`h`$, because you climb one parent per step from leaf to root.
- Insertion may stop early. For example, inserting 90 would not travel all the way up.
- Time: $`O(h) = O(\log n)`$. Space: $`O(1)`$ extra.
- The instructor's illustration: with 1000 nodes, $`\log_2 1000 \approx 10`$ comparisons.

### 2.6 Deletion (Delete Root + Sift-Down / Top-Down Heapify)

**Algorithm (max-heap, 1-based):**

```
DELETE(A, n):
    root ← A[1]
    A[1] ← A[n]                     // move last element to the root (keeps shape property)
    n ← n − 1
    i ← 1
    loop:
        l ← 2i ; r ← 2i + 1
        largest ← i
        if l ≤ n and A[l] > A[largest]: largest ← l
        if r ≤ n and A[r] > A[largest]: largest ← r
        if largest = i: break        // heap property satisfied
        swap A[i], A[largest]
        i ← largest
    return root
```

**Key rule:** compare the moved node with **both** children, and swap with the **larger** child (max-heap).

**Worked example (delete from the 9-node heap 95, 85, 45, 75, 25, 35, 15, 55, 65):**

1. Remove the root, 95. The root cannot stay empty, so move the **last** node, 65, into the root. The shape property is preserved.
2. Compare 65 with its children 85 and 45. The larger is 85, and $`85 > 65`$, so swap. 85 becomes the root and 65 moves to index 2.
3. Compare 65 with its new children 75 and 25. The larger is 75, and $`75 > 65`$, so swap.
4. 65 is now at index 4. Its child 55 is at index 8, and $`65 > 55`$. Index 9 no longer exists, so the heap property holds.

**Final tree:**
- The root is 85, with children 75 and 45.
- 75 has children 65 and 25.
- 45 has children 35 and 15.
- 65 has a single left child, 55.

**Complexity:**
- Removing the root is $`O(1)`$.
- Rebuilding follows one root-to-leaf path. That costs a small constant number of comparisons per level; the instructor said "into three", calling it constant. The total is $`O(3h) = O(h) = O(\log n)`$.
- The maximum number of interchanges is $`h`$, and the process may stop earlier.

### 2.7 Heap Sort (Using Repeated Deletion)

**Idea:**
- Each deletion extracts the current maximum.
- Instead of discarding it, **swap the root with the last element of the active heap** and shrink the heap size by 1.
- The maxima pile up at the end of the array, which produces an **ascending** sorted array with a max-heap.

**Algorithm:**

```
HEAPSORT(A, n):        // assumes A[1..n] is already a max-heap
    for size ← n down to 2:          // n − 1 deletions
        swap A[1], A[size]
        SIFT_DOWN(A, 1, size − 1)    // heap now occupies A[1..size−1]
```

**Worked trace (initial array 95, 85, 45, 75, 25, 35, 15, 55, 65):**

The symbol $`\mid`$ separates the active heap from the sorted tail.

- **Pass 1: swap 95 with 65.**
  - Array: $`65, 85, 45, 75, 25, 35, 15, 55 \mid 95`$.
  - Sift down: 65 vs (85, 45), so swap with 85. Then 65 vs (75, 25), so swap with 75.
  - 65 is now at index 4. Its child at index 8 is 55, and $`65 > 55`$, so stop.
  - Result: $`85, 75, 45, 65, 25, 35, 15, 55 \mid 95`$.
- **Pass 2: swap 85 with 55** (the last element of the active heap).
  - Array: $`55, 75, 45, 65, 25, 35, 15 \mid 85, 95`$.
  - Sift down: 55 vs (75, 45), so swap with 75. Then 55 at index 2 vs children at indices 4 and 5 (65, 25), so swap with 65.
  - 55 is now at index 4. Its child index is $`2\cdot 4 = 8 >`$ size 7, which is out of bounds, so stop.
  - Result: $`75, 65, 45, 55, 25, 35, 15 \mid 85, 95`$.
- **Continue:** after $`n-1`$ deletions, the array is fully sorted.

**Complexity:**
- Each deletion costs $`O(1)`$ for the swap plus $`O(\log n)`$ for the rebuild.
- There are $`n-1`$ deletions, so the total is $`O(n \log n)`$. The dominant term is taken as the upper bound.
- Space: $`O(1)`$ extra, because the sort happens in place.

**Note beyond the lecture:**
- The lecture started from an array that was *already* a heap.
- For a random array, you must first build a heap. Inserting the elements one by one costs $`O(n \log n)`$; bottom-up heapify costs $`O(n)`$.
- Overall, heap sort remains $`O(n \log n)`$.

### 2.8 Threaded Binary Trees

**Wasted null links:**
- In a linked binary tree with $`n`$ nodes, there are $`2n`$ link fields in total.
- Only $`n-1`$ of those links are used, one for each node except the root.
- The number of empty links is therefore:

```math
2n - (n-1) = n + 1
```

- **Class example:** a small tree with 3 nodes has 4 empty links. Adding one node fills one link but creates two new empty ones, giving 5.

**Idea:** reuse the null links as **threads**.
- A null **left** link points to the node's **in-order predecessor**.
- A null **right** link points to the node's **in-order successor**.

**Modified node structure** (described left to right):

| LTag (1 bit) | LC (left pointer) | Data | RC (right pointer) | RTag (1 bit) |
|---|---|---|---|---|

- If `LTag = 1`, LC is a **thread** to the in-order predecessor. If `LTag = 0`, LC points to the left child.
- If `RTag = 1`, RC is a **thread** to the in-order successor. If `RTag = 0`, RC points to the right child.
- Only **2 extra bits per node** are needed.

**Worked example.** The in-order traversal given in class is:

```math
B,\ A,\ G,\ E,\ D,\ F,\ C
```

The tree consistent with that traversal and with the threads discussed is reconstructed as follows. The ASR is garbled here, so treat the shape as a reconstruction.
- A is the root, with left child B and right child C.
- C has only a left child, D.
- D has left child E and right child F.
- E has only a left child, G.

**Threads:**

| Node | Left link | Right link |
|---|---|---|
| B | No predecessor (first in order), so a **dummy/header** node | Thread to its successor, **A** |
| G | Thread to its predecessor, **A** | Thread to its successor, **E** |
| E | Child G | Thread to its successor, **D** |
| F | Thread to its predecessor, **D** | Thread to its successor, **C** |
| C | Child D | No successor (last in order), so a **dummy** node |

- A student asked whether B's left link can point to A. The answer is no: A is not B's predecessor in the in-order sequence, so that link goes to a dummy node.
- The instructor noted that the slide contained copy-paste errors in some thread arrows. The two dummy links are the ones that were corrected.

**In-order traversal without a stack:**

```
INORDER_THREADED(root):
    p ← leftmost(root)          // keep following left child links (LTag = 0)
    while p ≠ dummy:
        visit(p)
        if p.RTag = 1:          // right thread → successor directly
            p ← p.RC
        else:                    // real right child → go to its leftmost node
            p ← leftmost(p.RC)
```

**Benefits:**
- No recursion is needed, and you do not have to keep track of parents on a stack. This means $`O(1)`$ extra space instead of $`O(h)`$.
- Finding the in-order predecessor or successor is easy, which helps **deletion** (replacing a node with its in-order predecessor or successor) and **traversal**.

## 3. Exam and Assignment Pointers

No explicit exam statement was made, but these points were emphasized or quizzed in class.

**Heap definition:**
- Know **both** properties: max/min ordering **and** complete/almost complete shape.
- Be ready to say why a given tree is or is not a heap.

**Index formulas:**
- 1-based: $`\text{left}(i) = 2i`$, $`\text{right}(i) = 2i+1`$, $`\text{parent}(i) = \lfloor i/2 \rfloor`$.
- 0-based: $`\text{parent}(i) = \lfloor (i-1)/2 \rfloor`$.
- Watch out for mixing the two conventions.

**Insertion position:**
- Always use the next slot that fills the last level from the left. "Left of 35, not left of 55" was a corrected student mistake.

**Maximum comparisons and swaps:**
- Both insertion and deletion take at most $`h`$ swaps, so they are $`O(h) = O(\log n)`$.
- During deletion, always swap with the **larger** child (max-heap).

**Deletion:**
- Called "the most important part."
- Only the root is deleted, and the last element is moved to the root.

**Heap sort:**
- Swap the root with the last element, shrink the size, and sift down.
- It takes $`n-1`$ deletions, for $`O(n \log n)`$ time.

**Threaded binary tree:**
- The instructor stressed: "you should know there is a concept of threaded binary tree."
- Know that there are $`n+1`$ null links, the role of the tag bits, and the rule that left threads point to the predecessor and right threads point to the successor.
