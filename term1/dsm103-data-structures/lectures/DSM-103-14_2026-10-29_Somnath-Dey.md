# DSM-103 · Session 14 — Binary Search Trees (BST)

**Instructor:** Somnath Dey · **Date:** 2026-10-29

---

## 1. Overview

The session opened with a short note about tree traversals (in-order, pre-order, post-order). These were covered last time, and students must study the algorithms from the slides. The main topic was the **Binary Search Tree (BST)**, a binary tree with an ordering property: everything in a node's left subtree is smaller than the node, and everything in its right subtree is larger.

The lecture covered:
- why this property speeds up searching;
- how search cost depends on tree shape ($O(\log n)$ for a complete tree, $O(n)$ for a skewed tree);
- the search and insertion algorithms, with worked examples;
- how to handle duplicate keys;
- how building a BST from sorted data produces a skewed tree;
- the difference between a BST and the binary search algorithm on a sorted array;
- the fact that in-order traversal of a BST gives a sorted sequence;
- deletion in its three cases (leaf, one child, two children), using the in-order successor or predecessor and a parent pointer.

It closed with a remark on rebuilding a BST from a single pre-order or post-order traversal.

### 2.1 Definition of a Binary Search Tree

**Binary tree:** each node has at most 2 children (0, 1, or 2).

There are special kinds of binary trees, each defined by a property it maintains: the **binary search tree**, the **heap tree**, and the **AVL tree**.

**BST property.** For every node (not only the root):
- all keys in its **left subtree** are **less than** the node's key;
- all keys in its **right subtree** are **greater than** the node's key.

The definition is **recursive**: the property must hold at every node, with that node treated as a "parent." The root is just a parent node that has no parent of its own.

> Student question: *"Can both children be greater than the parent?"*
> In a general binary tree, yes. In a BST, no. The left subtree must be smaller and the right subtree larger. That ordering is what makes it a BST.

**Example tree used in class.** Reconstructed from the worked examples; the slide figure is not available.

```
                65
              /    \
            19      74
              \       \
               28      88
              /  \
            25    57
```

- At 19, everything to the right (28, 25, 57) is greater than 19.
- At 28, the left subtree (25) is less than 28 and the right subtree (57) is greater than 28.

**Second example: months in alphabetical order.** The keys were month names (Jan, Feb, …), ordered as strings: compare the first character, then the second, and so on. This lets you find a given month quickly.

---

### 2.2 Why a BST helps searching

**Worked example: search for 25 in the tree above.**

1. Compare 25 with 65. Since $25 < 65$, go left. The whole right subtree is ignored, which roughly **halves the search space**.
2. Compare 25 with 19. Since $25 > 19$, go right. The left subtree of 19 is ignored.
3. Compare 25 with 28. Since $25 < 28$, go left.
4. Compare 25 with 25. Equal, so the key is found.

This takes **4 comparisons**. In a general binary tree with no ordering, you would not know which side holds the key. You might have to visit every node, which is much slower.

---

### 2.3 When the BST gives no benefit: skewed trees

- If keys are inserted as 105, 95, 85, …, each new key becomes the left child of the previous one. The result is a **left-skewed BST**: a chain.
- This is still a valid BST, but searching it (e.g., for 105 at the bottom of a chain) means visiting **every node**. There is no gain over a plain list.
- **Fix:** use **height-balanced trees (AVL trees)**. These were mentioned but **not covered** in this course.

---

### 2.4 Search complexity

For a BST of height $h$:

$$\text{max comparisons to find a key} \approx h \quad\Rightarrow\quad T_{\text{search}} = O(h)$$

**Complete BST with $n$ nodes.** From earlier theorems, its height is logarithmic:

$$h = O(\log n) \quad\Rightarrow\quad T_{\text{search}} = O(\log n)$$

This is a large reduction compared with $n$.

**Skewed BST.** Every node is on one chain, so:

$$h = O(n) \quad\Rightarrow\quad T_{\text{search}} = O(n)$$

In this case you may need about $n$ comparisons.

| Tree shape | Height $h$ | Search time |
|---|---|---|
| Complete / balanced | $O(\log n)$ | $O(\log n)$ |
| Skewed (left or right) | $O(n)$ | $O(n)$ |

Insertion and deletion first walk down the tree the same way, so they also cost $O(h)$. The lecture implied this, though only search complexity was stated explicitly.

1. Searching for a key
2. Inserting a key
3. Deleting a key
4. Traversal: in-order, pre-order and post-order work exactly as for any binary tree (already covered).

### 2.6 Search Algorithm

**Logic.** At the current node there are three cases:
- **key = node value:** return a pointer to this node;
- **key < node value:** continue in the **left** subtree;
- **key > node value:** continue in the **right** subtree.

**Stopping criterion:** stop when the key is found, or when you reach a **null pointer** (the key is not present).

**Worked example 1: search for 57.**
- $57 < 65$, so go left.
- $57 > 19$, so go right.
- $57 > 28$, so go right.
- $57 = 57$. Found; return the pointer.

**Worked example 2: search for 58.**
- $58 < 65$, so go left.
- $58 > 19$, so go right.
- $58 > 28$, so go right.
- $58 > 57$, so go right, but the right child of 57 is null. Stop: the item does not exist.

**Pseudocode (iterative, as on the slide):**

```
SEARCH-BST(root, item)
1.  ptr  <- root
2.  flag <- FALSE
3.  while (ptr != NULL) and (flag == FALSE) do
4.      if item < ptr.data then
5.          ptr <- ptr.left          // go to left subtree
6.      else if item == ptr.data then
7.          flag <- TRUE             // found
8.      else                         // item > ptr.data
9.          ptr <- ptr.right         // go to right subtree
10. end while
11. if flag == TRUE then
12.     return ptr                   // search successful
13. else
14.     print "Item does not exist"  // loop ended because ptr == NULL
```

How the loop ends:
- It exits because `flag == TRUE`, meaning the key was found, or
- it exits because `ptr == NULL`, meaning the end of a path was reached and the key is absent.

**Complexity:** time $O(h)$, which is $O(\log n)$ when balanced and $O(n)$ when skewed. The iterative version uses $O(1)$ extra space.

---

### 2.7 Insertion Algorithm

**Logic.**
1. Follow the same path as a search.
2. Continue until you reach a **null** position.
3. Attach the new node there, as the left or right child of the last node visited.

**Worked example 1: insert 90.**
- $90 > 65$, so go right to 74.
- $90 > 74$, so go right to 88.
- $90 > 88$, and the right child of 88 is null. Insert 90 as the **right child of 88**.

**Worked example 2: insert 52.**
- $52 < 65$, so go left.
- $52 > 19$, so go right.
- $52 > 28$, so go right.
- $52 < 57$, and the left child of 57 is null. Insert 52 as the **left child of 57**.

**Pseudocode (no duplicates allowed, as on the slide):**

```
INSERT-BST(root, key)
1.  if root == NULL then
2.      root <- new node(key); return
3.  ptr <- root ; parent <- NULL
4.  while ptr != NULL do
5.      if key == ptr.data then
6.          print "Item already exists"; return    // duplicate check
7.      parent <- ptr
8.      if key < ptr.data then
9.          ptr <- ptr.left
10.     else
11.         ptr <- ptr.right
12. end while
13. newNode <- new node(key)       // left = right = NULL
14. if key < parent.data then
15.     parent.left  <- newNode
16. else
17.     parent.right <- newNode
```

- The first part (steps 3–12) is essentially a search that moves the pointer to the null position.
- The last part (steps 13–17) attaches the new child.

**Complexity:** time $O(h)$.

---

### 2.8 Duplicate Keys

**Example question:** where does a second 28 go? The answer depends entirely on how the comparison is coded.

- **Code uses `if key < ptr.data go left; else go right`.** Here "else" means $\geq$, so a duplicate goes into the **right subtree of the first 28**.
  - Trace: $28 < 65$ → left. $28 > 19$ → right. $28 = 28$ → right (to 57). $28 < 57$ → left (to 52). $28 < 52$ → left.
  - Result: the duplicate ends up as the **left child of 52**.
- **Code uses `if key <= ptr.data go left`.** The duplicate goes into the **left subtree of the first 28**.
- **To forbid duplicates,** add a check before the comparison:
  `if key == ptr.data: report "duplicate data present, insertion not possible"`.

**Convention:** BSTs normally **do not store duplicates**. With duplicates, searching or deleting is ambiguous: if there are two 28s, which one do you mean? Allowing duplicates is a special case that needs special handling.

---

### 2.9 Building a BST from a Sequence; Sorted Input

**Example sequence:** 20, 25, 27, 30, 40, 50, inserted one by one into an empty BST.
- 20 becomes the root.
- 25 becomes the right child of 20.
- 27 becomes the right child of 25.
- …and so on until 50.

Picture a straight chain going down to the right:

```
20
  \
   25
     \
      27
        \
         30
           \
            40
              \
               50
```

| Input order | Shape of the BST |
|---|---|
| Ascending | **Right-skewed** BST |
| Descending | **Left-skewed** BST |
| Random | Roughly **balanced** BST |

A BST built from sorted data gives **no search advantage**. For data that is already sorted, use the **binary search algorithm on the array** instead.

---

### 2.10 Binary Search Tree vs. Binary Search Algorithm

These are **different things.**

- **Binary search tree:** a tree that satisfies the BST property. You search by walking down the tree.
- **Binary search algorithm:** works on a **sorted array**, in ascending or descending order.

**Sequential (linear) search**, for comparison. To find 27 in 20, 25, 27, 30, 40, 50, compare with 20, then 25, then 27, where it is found. This is $O(n)$.

**Binary search on a sorted array:**
1. Take the **middle** element.
2. If key = mid, it is found.
3. If key < mid, search only the **left half**, since all those elements are smaller.
4. If key > mid, search only the **right half**.
5. Repeat on the chosen half until the key is found or the range is empty.

```
BINARY-SEARCH(A[low..high], key)
while low <= high:
    mid <- (low + high) / 2        // integer division
    if A[mid] == key: return mid
    else if key < A[mid]: high <- mid - 1
    else: low <- mid + 1
return NOT FOUND
```

The midpoint index is $\text{mid} = \left\lfloor \frac{\text{low} + \text{high}}{2} \right\rfloor$. Time is $O(\log n)$.

**Requirement:** the array **must be sorted** (ascending or descending).

---

### 2.11 In-order Traversal of a BST is Sorted

**Key fact:** the in-order traversal of **any** BST gives its keys in **ascending sorted order**.

So after any insertion or deletion, the tree must still produce a sorted in-order sequence. This is the guiding principle for deletion.

Pre-order and post-order traversals of a BST show **no particular order**: the sequence looks random.

---

### 2.12 Deletion — the Three Cases

**Example tree for deletion.** Reconstructed from the in-order sequence given in class: 16, 20, 24, 27, 29, 33, 35, 42, 45.

```
                35
              /    \
            20      45
           /  \     /
         16    29  42
              /  \
            24    33
              \
               27
```

In words:
- Root 35 has left child 20 and right child 45.
- 20 has children 16 (left) and 29 (right).
- 29 has children 24 (left) and 33 (right).
- 24 has only a right child, 27.
- 45 has only a left child, 42.

#### Case 1: The node is a leaf (no children)

- Delete it directly. The in-order order is not affected.
- Example: deleting a leaf such as 27, 16, 33 or 42 just removes it from the sorted sequence.
- Implementation: set the **parent's** corresponding child pointer (left or right) to NULL.

#### Case 2: The node has exactly one child

- Replace the node with its only child, i.e., connect the parent directly to that child.
- **Example: delete 45**, which has only the left child 42.
  - Using 35 to fill the gap would break the order.
  - Using 42 works. Put 42 in 45's place; the old 42 node is a leaf and is simply removed.
  - The tree becomes 35 → right child 42.
- **Example: delete 24**, which has only the right child 27. Replace it with 27, so 27 becomes the left child of 29.

#### Case 3: The node has two children

Replace the node with its **in-order successor** or its **in-order predecessor**, then delete that successor or predecessor node from its old position.

**Definitions:**
- **In-order predecessor** of $x$: the node visited **just before** $x$ in in-order traversal. It is the **rightmost node of $x$'s left subtree**.
- **In-order successor** of $x$: the node visited **just after** $x$ in in-order traversal. It is the **leftmost node of $x$'s right subtree**.

Examples from the original tree:
- Predecessor of 29 is **27**; successor of 29 is **33**.
- Predecessor of 35 is **33** (rightmost of 35's left subtree).
- For 20: predecessor is 16, successor is 24.

**Which replacements are valid for 20?** Use the in-order sequence 16 **20** 24 27 29 33 35 42 45.
- Fill with 16 (predecessor): valid.
- Fill with 24 (successor): valid.
- Fill with 29: invalid. The in-order sequence would no longer be ascending, or much more restructuring would be needed.

**Important property:** when the deleted node has two children, its in-order successor or predecessor has **at most one child**. The successor is the leftmost node of the right subtree, so it has no left child; otherwise that left child would be the successor. The predecessor is the rightmost node of the left subtree, so it has no right child. Removing the successor or predecessor is therefore always Case 1 or Case 2.

**Worked example: delete 20, using the in-order successor.**
1. The in-order successor of 20 is 24, the leftmost node of 20's right subtree (29 → 24).
2. Copy 24 into 20's position.
3. Delete the old 24 node. It has one child (27), so this is Case 2: connect 27 to 29 as its left child.

Resulting tree:

```
                35
              /    \
            24      45
           /  \     /
         16    29  42
              /  \
            27    33
```

The in-order sequence is now 16, 24, 27, 29, 33, 35, 42, 45, still sorted.

> Student question: *"Before deletion 24 was a child (descendant) of 29; afterwards 24 is an ancestor of 29. Is that okay?"*
> Yes. Only the BST property matters. Everything in 24's right subtree (27, 29, 33) is greater than 24, so the property holds.

> Student question: *"Why not just move the left child up into the deleted node's place?"*
> Moving the left child up leaves a hole that must be filled again. In a large complete tree this repeats at every level, which is costly. Using the successor or predecessor needs at most one extra removal, and that removal is always the easy Case 1 or Case 2.

#### Deletion algorithm (step by step)

1. **Search** for the key using the BST search. While descending, also keep a **parent pointer** that always points to the parent of the current node.
2. If the key is not found, report it and stop.
3. **Determine the case** at the found node `ptr`:
   - `ptr.left == NULL and ptr.right == NULL`: **Case 1**.
   - exactly one of `ptr.left`, `ptr.right` is NULL: **Case 2**.
   - both non-NULL: **Case 3**.
4. **Case 1:** set `parent.left` or `parent.right` (whichever points to `ptr`) to NULL.
5. **Case 2:** set the parent's pointer to `ptr`'s only child.
6. **Case 3:**
   - find the in-order successor `s`, the leftmost node of `ptr.right`, while also tracking `s`'s parent;
   - copy `s.data` into `ptr`;
   - delete `s` using Case 1 or Case 2.

```
DELETE-BST(root, key)
1.  parent <- NULL ; ptr <- root
2.  while ptr != NULL and ptr.data != key:       // search, tracking parent
3.      parent <- ptr
4.      if key < ptr.data: ptr <- ptr.left else: ptr <- ptr.right
5.  if ptr == NULL: print "Item not found"; return
6.  if ptr.left != NULL and ptr.right != NULL:   // CASE 3
7.      sParent <- ptr ; s <- ptr.right
8.      while s.left != NULL:                    // leftmost of right subtree
9.          sParent <- s ; s <- s.left
10.     ptr.data <- s.data                       // copy successor up
11.     ptr <- s ; parent <- sParent             // now delete s (case 1 or 2)
12. if ptr.left != NULL: child <- ptr.left       // CASE 2 or CASE 1
13. else: child <- ptr.right                     // child = NULL for a leaf
14. if parent == NULL: root <- child             // deleting the root
15. else if parent.left == ptr: parent.left <- child
16. else: parent.right <- child
17. free(ptr)
```

**Why the parent pointer is needed:** a node is removed by changing its **parent's** left or right pointer to NULL or to the child. Without a reference to the parent you cannot unlink the node. Example: to delete 27 (a leaf), you must set `24.right` to NULL.

**Complexity:** $O(h)$. That is one downward search, plus at most one further walk down to find the successor.

---

### 2.13 Reconstructing a BST from One Traversal

- For a **general** binary tree, two traversals are needed to rebuild it uniquely, for example in-order together with pre-order or post-order.
- For a **BST**, one traversal is enough. If you are given only the pre-order or only the post-order, **sort** that data to get the in-order sequence. You then have two traversals and can rebuild the tree.
- This is not on the slides but was presented as something students now know.

## 3. Exam / Assignment Pointers

- **Traversal algorithms** (in-order, pre-order, post-order) on the slides **must be studied**. They were not explained line by line in class.
- Know the **BST property** and that it applies **recursively at every node**.
- **Search complexity:** $O(h)$, which is $O(\log n)$ for a complete or balanced BST and $O(n)$ for a skewed BST.
- **Sorted input gives a skewed BST:** ascending input makes a right-skewed tree and descending input makes a left-skewed tree.
- **Do not confuse** a binary search tree with the binary search algorithm (sorted array, midpoint comparison).
- **In-order traversal of a BST is always ascending.** Pre-order and post-order show no order.
- **Deletion has three cases** (leaf, one child, two children). Know the in-order successor and predecessor definitions and where to find them:
  - successor = leftmost node of the right subtree;
  - predecessor = rightmost node of the left subtree.
- The successor or predecessor of a node with two children has **at most one child**.
- **Duplicates:** know how `<` versus `<=` changes where a duplicate goes, and that BSTs conventionally reject duplicates.
- Be able to **trace** search, insert and delete on a given tree, and to **build a BST** from a given key sequence.
- **Rebuilding a BST** from only a pre-order or post-order traversal: sort it to get the in-order sequence.
